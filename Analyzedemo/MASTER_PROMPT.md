## 3. プロジェクト概要

不審なWebリクエストに対する、**AI支援型の検知および説明機能を実証する、ローカル環境でテスト可能なサイバーセキュリティアプリケーション**を構築してください。

意図的に脆弱性を含むWebアプリケーションである **OWASP Juice Shop** を、隔離されたローカルDocker環境上でデモ用ターゲットとして使用します。

システムには以下の機能を組み合わせます。

1. 不審なリクエストに対するルールベース検知とAI支援型検知
2. リクエストデータのサニタイズおよび安全な処理
3. 利用可能な場合、GitHub Copilot SDKを使用した任意のAI説明
4. イベント、検知結果、説明を表示するダッシュボード
5. テストケースおよび評価指標
6. エクスポート可能なレポート
7. セキュリティおよびプライバシー対策
8. 再現可能なセットアップ手順と完全なデモワークフロー

このプロジェクトにおける最重要原則は以下です。

> **観測された事実、ルールベースの検知結果、AIが生成した仮説を明確に分離して表示すること。**

AI検知の判定結果もルールベース検知結果と区別して保持・表示し、説明文やAIの判定を観測された事実として扱ってはいけません。

AIによる出力を、攻撃が実際に発生したことの証拠として扱ってはいけません。

このプロジェクトは、大学・研修などの評価環境で安全にデモできるようにし、外部システムを攻撃対象としてはいけません。

## 4. セキュリティ範囲と許可された環境

OWASP Juice Shopは、ローカルマシンまたは明示的に許可された隔離環境上で動作する、意図的に脆弱なデモアプリケーションとしてのみ使用してください。

デフォルトでは、以下のようなlocalhostまたはループバックインターフェイスを使用してください。

```text
127.0.0.1
localhost
```

### 要件

- 公開IPアドレスや無関係な外部Webサイトをスキャンしない
- 許可されていない脆弱性悪用を行わない
- 実際のユーザー認証情報やセッショントークンを収集しない
- 認証情報窃取、永続化、ステルス化、マルウェア、破壊的処理を実装しない
- デフォルト構成ではJuice Shopをインターネットに公開しない
- ターゲットに対する攻撃処理を自動実行しない
- リクエストログから取得した任意のペイロードを実行しない
- AIモデルによって生成された信頼できないシェルコマンドを実行しない
- デモを簡単にする目的でセキュリティ制御を無効化しない
- このシステムが認定済みIDS製品ではなく、**防御を目的とした教育用デモシステム**であることを明確に説明する

Dockerが利用できない場合でも評価・デモできるよう、**安全なモックイベントモード**を用意してください。

またダッシュボードでは、以下を明確に区別してください。

- 実際に観測されたデータ
- モックデータ
- 合成データ

## C. ハイブリッド検知エンジン（ルールベース＋AI）

不審なリクエストパターンを検知する、ルールベース検知とAI支援型検知を組み合わせたモジュール化エンジンを実装してください。両方の検知経路を独立して実行し、それぞれの判定、根拠、状態を個別に保存してください。片方の結果で他方の結果を上書きしてはいけません。

### AI支援型検知

- 入力データから不審なリクエストや通常と異なるパターンを判定するAI検知コンポーネントを用意してください。
- ローカルで実行できる統計的・機械学習的手法を優先し、デモデータや評価用データで再現可能にしてください。利用可能なデータや環境に応じて手法を選び、根拠なく高い精度を主張してはいけません。
- 外部AIの説明機能は明示的に有効化し、ユーザーがイベントごとに要求した場合だけ、サニタイズ済みの最小限のデータを送信してください。外部AIが利用できない場合も、ルールベース検知とローカル統計AI検知は継続してください。
- AI検知結果には、判定状態、対象カテゴリ、スコアまたは信頼度（算出できる場合）、判定に使った入力の要約、制限事項を含めてください。スコアを確率として誤認させないよう、意味と尺度を説明してください。
- AIは攻撃の成功や侵害を確定できません。AI検知結果は調査の手掛かりとして扱い、観測事実やルール一致の証拠と混同しないでください。
- AIのタイムアウト、モデル未設定、利用不可、エラー時は状態を記録し、アプリケーション全体を停止させず、ルールベースの結果を利用できるようにしてください。

### 検知結果の統合

- ルール検知とAI検知の結果は別々に保持し、ダッシュボードとエクスポートで検知元を確認できるようにしてください。
- いずれか一方が不審と判定した場合も、その検知元と根拠を明示してください。両方が一致した場合は両方の根拠を併記してください。
- ルールとAIが異なる判定をした場合は不一致として明示し、根拠のない単一スコアや「攻撃確定」判定にまとめないでください。
- 全体の表示用判定が必要な場合は、その統合ルールを文書化・テストし、元の個別判定を失わないようにしてください。

### 教育目的の検知カテゴリ

以下のようなパターンに対応してください。

- SQLインジェクションの兆候
- クロスサイトスクリプティング（XSS）の兆候
- パストラバーサルの兆候
- 不審な認証関連リクエストパターン
- 想定外または不正な形式のリクエスト
- 利用可能なイベントデータがある場合、繰り返される不審リクエスト

可能な範囲でルールを設定可能な構造にしてください。

### 各ルールについて記録する内容

- Rule ID
- Rule Name
- Purpose
- Pattern / Condition
- Severity
- Evidence
- Known Limitations
- False-positive Considerations

すべての攻撃カテゴリを単純なキーワードチェックだけで判定する設計にはしないでください。

以下を適切に組み合わせてください。

- 正規化
- 入力検証
- 適切にテストされたパターンマッチング

パターンマッチングによって、すべての攻撃を検出できる、または悪意を確定できるとは説明しないでください。

### ユニットテスト

以下に対応するテストを作成してください。

- 正常なリクエスト
- 不審なリクエスト例
- エンコードされた入力
- 不正形式入力
- エッジケース
- False Positive（誤検知）の可能性があるケース
- AI検知の正常・不審な入力、利用不可・エラー時の動作
- ルールとAIが一致するケース、および判定が食い違うケース
- AI検知が無効または失敗してもルール検知結果が保持されること

AI検知を評価する場合は、ラベル付きテストデータを用いて適切な指標（例：Precision、Recall、False Positive Rate）を報告し、データの範囲や限界を明記してください。テストデータでの評価を実運用の性能として表現してはいけません。

## D. サニタイズとプライバシー

Copilot SDKへ送信する前、または機密情報を表示すべきでない場所で使用する前に、専用のサニタイズ処理を実行してください。ローカルAI検知にも必要最小限のサニタイズ済みデータを渡し、検知のために機密情報を不必要に保持しないでください。

### サニタイズ層の要件

以下の情報を削除またはマスキングしてください。

- パスワード
- Authorization Header
- Bearer Token
- Cookie
- Session ID
- API Key
- Secretと思われる値
- 識別可能な機密個人情報

また、以下を実施してください。

- リクエストBodyは明確に必要な場合を除いて送信しない
- Bodyを利用する必要がある場合は安全にサニタイズする
- 入力文字数を制限する
- ログインジェクションを防止する
- 危険なレンダリングを防止する
- 想定外の入力でもアプリケーションがクラッシュしないようにする

単純な正規表現を通過したという理由だけで、リクエスト全体が安全だと判断してはいけません。

### データ最小化

Copilotには、明示的に要求された説明に必要なフィールドだけを送信してください。外部AIへの送信は任意とし、ローカルのルールベース検知およびローカルAI検知を利用するための必須条件にしてはいけません。

生の機密リクエストデータを不必要に保存してはいけません。

以下についてドキュメント化してください。

- サニタイズ処理
- サニタイズの限界
- 外部AIサービスへ送信されるデータ

## E. GitHub Copilot SDKによるAI説明

GitHub公式のCopilot Python SDK (`github-copilot-sdk`)を使用し、ローカルで認証済みのCopilot CLIランタイムを介して説明を生成してください。これはAPIキー付きの単純なHTTPモデルクライアントではなく、Copilotのエージェントランタイムを呼び出すSDKです。ローカル統計AI検知の代替にはせず、イベント説明だけに使用してください。

実装前に[Copilot SDK公式資料](https://github.com/github/copilot-sdk)、Python SDKの要件、認証方法、利用枠を確認してください。SDKのモデル一覧から利用可能なものを選び、モデル名を永久固定の前提にしないでください。`COPILOT_MODEL`で選択可能にし、既定値は`auto`とします。

### 有効化と認証

- `COPILOT_ENABLED=false`を既定値とし、`.env`でユーザーが明示的に有効化する
- ローカルのCopilot CLIログイン済みユーザー認証を利用し、アプリにGitHubトークンや個人アクセストークンを貼り付けさせない
- 実行時に認証が必要な場合は、トークンを表示・保存・ログ出力せず、ローカルCLIの認証状態を確認する案内を表示する
- `.env.example`には`COPILOT_ENABLED`と`COPILOT_MODEL`だけを記載し、`.env`をGit対象外にする
- SDKは初回実行時にランタイムを取得する場合がある。取得先・通信・組織ポリシーをREADMEへ記載する

### 安全な実行境界

- Copilot SDKは`mode="empty"`で起動し、`available_tools=[]`および`tools=[]`を指定する
- Shell、ファイル操作、MCP、Skills、GitHubキャッシュなどのツールを有効にしない
- セッションメモリ、セッションストア、無限セッション、不要なテレメトリを無効にする
- イベント本文や任意フィールドは渡さず、サニタイズ済みpath、method/status、ルール根拠、ローカル統計AIの判定だけを送信する
- 一覧表示やインポート時に自動送信せず、ユーザーがSettingsで同意し、イベント詳細の説明操作を行った場合だけ呼び出す
- Copilotへの各要求は利用プランの要求枠を消費する場合がある。モデル別の倍率や上限は変化するため、最新の公式プラン・利用状況を確認する。無料枠や無制限利用を前提にしない
- 別モデルやBYOKへの自動フォールバック、自動再試行を行わない。ユーザーの明示操作1回につき要求を1回だけ送る

### 呼び出し失敗と説明結果

以下に対応してください。

- 応答Timeoutおよびランタイム停止
- Copilot CLI未導入/ランタイム取得失敗
- ローカル認証なし、失効または利用権限なし
- 利用不可モデル、利用枠超過、Rate Limit
- ネットワーク障害、不正・空応答

エラーには認証情報やSDK内部の生レスポンスを含めず、状態と安全な利用者向け案内だけを記録してください。失敗時もルール検知とローカル統計AIの結果を保持し、サニタイズ済み入力の説明結果だけをプロセス内で適切にキャッシュしてください。

### AIが提供する内容

AI検知が有効な場合、AIは不審度や対象カテゴリの判定と、その判断に使った入力上の根拠・不確実性を返してください。加えて、利用可能な場合は以下の説明を提供してください。

1. 検知されたパターンについての平易な説明
2. なぜそのイベントが不審である可能性があるのか
3. 観測された証拠とAIによる解釈の明確な区別
4. 意味がある場合の信頼度についての説明
5. False Positiveとなり得る理由
6. 推奨される防御側の調査手順
7. 制限事項および不確実性

### AI出力に関する重要原則

AIは、イベントデータに存在しない情報を作り出してはいけません。

また、AIによる検知結果および説明は**攻撃の確定情報として扱わず、ルールベース検知と並行する補助的な判定・仮説として扱ってください。**AIの判定によってルール検知の証拠を書き換えたり、ルール検知の結果を隠したりしてはいけません。

---

## 7. プロジェクト全体の基本原則

本システムでは、常に情報を以下の4種類に分類してください。

### ① 観測された事実

実際にイベントデータから確認できる情報。

例：

```text
HTTP Method: GET
Status Code: 400
Matched Rule: SQLI-001
Source: Local Observation
```

### ② ルールベース検知結果

検知エンジンによってパターン一致した結果。

例：

```text
Detection Category: SQL Injection Indicator
Severity: High
Rule ID: SQLI-001
```

これは「SQLインジェクション攻撃が実際に成功した」という意味ではありません。

### ③ AI支援型検知結果

AI検知コンポーネントが入力データから導いた判定、スコア、カテゴリなど。算出方法や限界を示し、ルール検知結果とは別に表示してください。

例：

```text
AI Detection: Suspicious
Score: 0.82 (モデル固有の尺度。確率とは限らない)
Evidence: リクエスト特徴量が評価用データの不審パターンに類似
```

これは「攻撃が実際に発生した、または成功した」という意味ではありません。

### ④ AIによる解釈・仮説

GitHub Copilot SDKによる補足説明。

例：

```text
このリクエストにはSQL構文として解釈される可能性のある
パターンが含まれているため、不審なリクエストとして
調査対象にすることが考えられます。

ただし、この情報だけでは実際の攻撃や侵害を確定することはできません。
```

これら4つをダッシュボード・レポート・ドキュメント上で混同しないようにしてください。ルールとAIの判定が食い違う場合も、両方の結果とその状態を確認できるようにしてください。
