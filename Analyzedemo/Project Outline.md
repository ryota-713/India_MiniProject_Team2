# プロジェクト概要：AI支援型サイバー攻撃検知・説明システム

**プロジェクト種別：** AI + サイバーセキュリティ + Webアプリケーション  
**チーム人数：** 3名  
**主要技術：** Python、Streamlit、GitHub Copilot SDK、Docker、OWASP Juice Shop、GitHub  
**目標：** テスト、ドキュメント、ライブダッシュボードを備え、ローカル環境で実際にデモできるサイバーセキュリティアプリケーションを構築する。

---

## 1. このプロジェクトは何をするものか？

私たちのプロジェクトは、**「AI支援型サイバー攻撃検知・説明システム」**です。

不審なWebリクエストを特定し、それらがなぜサイバー攻撃の可能性があるのかを分かりやすく説明することを目的としています。

従来のルールベースのセキュリティシステムでは、リクエスト内に存在する既知のパターンを検出します。このようなシステムは不審な動きを検知できますが、検知結果が何を意味しているのか、初心者には理解しにくい場合があります。

そこで本プロジェクトでは、次の2つのアプローチを組み合わせます。

1. **ルールベース検知：** あらかじめ定義されたセキュリティルールを使用して、不審なパターンを検知します。
2. **AI支援型検知・説明：** ローカル統計AIも検知に使い、GitHub Copilot SDKで検知されたパターンを分かりやすく説明して防御側の調査手順を提案します。

結果はWebダッシュボード上に表示します。ユーザーはイベントを確認し、検知の根拠を確認し、考えられるリスクを理解したり、結果をフィルタリングしたり、レポートとしてエクスポートしたりできます。

プロジェクトのデモは、合成されたセキュリティイベントを使用し、利用可能な場合にはローカル環境のOWASP Juice Shopを使用して安全に実施します。

---

## 2. 解決したい課題

Webアプリケーションには、以下のような潜在的に危険なパターンを含むリクエストが送信されることがあります。

- SQLインジェクションの試行
- クロスサイトスクリプティング（XSS）の兆候
- パストラバーサルの試行

しかし、不審なパターンを検知するだけでは、その検知結果が何を意味するのかを十分に説明できるとは限りません。

また、セキュリティシステムによる検知には**誤検知（False Positive）**が含まれる可能性があります。さらに、AIモデルの出力を検証済みの事実として扱ってしまうと、AIが誤った結論を出す可能性もあります。

そこで本プロジェクトでは、以下を実現する教育目的の防御システムを開発します。

- 特定の不審なリクエストパターンを検知する
- 各ルールベース検知について根拠を提示する
- AIを使用して考えられるリスクを説明する
- 検証済みの観測事実とAIが生成した仮説を明確に分離する
- 分かりやすいダッシュボードで検知結果を表示する
- ラベル付きテストデータを使用して検知性能を評価する
- データ処理中の機密情報を保護する

## 3. 主な目標

1. 実際に動作するサイバーセキュリティダッシュボードを構築する
2. モジュール化されたルールベース検知エンジンを実装する
3. 特定の不審なWebリクエストパターンを識別する

5. AIによる分析前に機密情報をサニタイズする
6. イベントの重大度、根拠、説明を表示する
7. 検知結果の検索、フィルタリング、エクスポートを可能にする
8. テストデータを使用して検知性能を測定する
9. 管理されたローカル環境でシステムをデモする
10. 3名全員がGitHub上で実際の開発に貢献する

## 4. プロジェクトはどのように動作するのか？

全体的な処理の流れは以下のとおりです。

### 1. イベント入力

**入力対象：**

- 合成イベント
- 検証済みのCSV / JSONファイル
- 許可されたローカル環境からの観測データ

↓

### 2. 検証とサニタイズ

入力フィールドを検証するとともに、以下のような機密情報を削除・マスキングします。

- トークン
- パスワード
- Cookie
- その他の機密データ

↓

### 3. ルールベース検知エンジン

不審なパターンが存在するかを確認し、以下を記録します。

- 一致したルール
- 検知の根拠

↓

### 4A. ルールベースの検知結果

以下を表示します。

- 観測されたデータ
- 一致したルール
- 重大度
- 検知の根拠

### 4B. GitHub Copilot SDK

ユーザーが説明を明示的に要求した場合に限り、サニタイズ済みイベントデータを使ってCopilotによる説明を生成します。

Copilotはイベントの意味や考えられるリスクを説明します。ルール検知とローカル統計AIはCopilotなしでも動作します。

↓

### 5. Webダッシュボード

ダッシュボードでは以下を行えるようにします。

- イベントの確認
- 検知根拠とAI説明の比較
- 検知結果のフィルタリング
- レポートのエクスポート

### 重要事項

**ルールベース検知エンジンがシステムの中核です。**

Copilot SDKは、あくまでオプションの「説明レイヤー」であり、唯一の検知手段ではありません。

Copilot SDK、CLI認証、または利用枠に問題がある場合でも、ルールベース検知、ローカル統計AI、ダッシュボードは引き続き動作できるようにします。

初期バージョンでは、提供されたイベントおよび許可されたローカル環境からの観測データを処理します。

別途、適切に許可されたデータ収集機能が実装・テストされていない限り、コンピューター上のすべての通信を自動監視する機能は実装しません。

## 5. どのような不審な活動を検知するのか？

| 検知カテゴリ | システムが検知する内容 |
|---|---|
| SQLインジェクションの兆候 | データベースクエリを不正に操作しようとする試みに関連するリクエストパターン |
| クロスサイトスクリプティング（XSS）の兆候 | ブラウザ上で実行可能なコンテンツを注入しようとするパターン |
| パストラバーサルの兆候 | 本来アクセスできるディレクトリの外部へアクセスしようとする試み |
| 認証関連の異常 | 適切なデータが利用できる場合における、不審または繰り返される認証リクエストパターン |
| 不正形式のリクエスト | 無効または通常とは異なる構造のリクエスト |
| 繰り返される不審な活動 | タイムスタンプとイベント履歴が利用できる場合、一定時間内に発生した複数の不審イベント |

これらはあくまで**パターンベースの兆候**であり、攻撃が実際に成功したことを証明するものではありません。

また、システムでは正常なリクエストが不審なパターンと似ている場合、誤検知となる可能性についても考慮する必要があります。

## 6. Webサイトはどのような構成になるのか？

WebサイトはStreamlitを使用したダッシュボードとして構築します。

### ダッシュボード概要

以下の情報を表示します。

- プロジェクトタイトルとシステム状態
- 処理したイベント総数
- 不審イベント数
- 重大度別イベント数
- 最近のイベント一覧
- 検知カテゴリによるフィルター
- 検索と並び替え
- AI機能の利用可能状態
- 合成データと実際の観測データの明確な区別

### イベント詳細ページ

ユーザーがイベントを選択すると、以下を表示します。

- サニタイズ済みリクエスト情報
- 検知カテゴリと重大度
- 一致したルール
- 検知結果を裏付ける根拠
- 利用可能な場合はAI生成による説明
- 誤検知となる可能性がある理由
- 推奨される防御対応
- データ処理またはAIに関するエラー情報

### その他のページ・セクション

#### Upload Events
対応するCSVまたはJSONファイルをインポートします。

#### Detection Rules
利用可能な検知ルールと、それぞれの目的を確認します。

#### Evaluation
必要に応じて、以下の測定結果を確認します。

- Precision（適合率）
- Recall（再現率）
- F1-score
- Confusion Matrix（混同行列）

#### Reports
サニタイズ済みの検知結果をエクスポートします。

#### Settings
秘密情報を公開することなく、システム設定やサービスの利用可能状況を確認します。

インターフェイスは、見やすく分かりやすいデザインとし、大学などでのライブデモにも適したものにします。

実際の担当については、それぞれの得意分野についてチームで話し合った後、調整することができます。

**主な責任：サイバーセキュリティのコアロジックを構築する**

#### タスク

- イベントデータ構造の定義
- イベントの入力検証の実装
- 検知ルールの開発

## 9. GitHub共同開発計画

プロジェクトでは、1つの中央GitHubリポジトリを使用します。

各メンバーは自分自身のGitHubアカウントを使用し、実際の開発作業に貢献します。

### 推奨ワークフロー

1. 各タスクについてGitHub Issueを作成する
2. Issueを担当メンバーに割り当てる
3. 可能な範囲でFeature Branchを使用して作業する
4. 意味のある単位で変更をCommitする
5. Pull Requestを作成してレビューする
6. Mergeする前にテストを実行する
7. `CONTRIBUTIONS.md`に実際に完了した作業を記録する

最終的な貢献記録には、各メンバーについて以下を記載します。

- プロジェクト内での役割
- 完了したタスク
- 関連するCommitまたはPull Request
- 実施したテスト
- ドキュメントへの貢献
